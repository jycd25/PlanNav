# @ds/bench

The friction benchmark for PlanNav. Ground truth for the planner experiments. **Read-only during experiment runs**: scenarios, dialogues, weights, and scorer are frozen so that experiments optimize the product, not the ruler.

```
pnpm bench                                  # Tier A on the instance scenarios (scenarios/*.json): the baseline week and its operations; deterministic, seconds
node --disable-warning=ExperimentalWarning packages/bench/run.mjs
node packages/bench/run.mjs --suggest       # Tier A on the from-scratch scenarios (scenarios/suggest/*.json): plan_schedule, the suggest path
node packages/bench/run.mjs --timelines     # also print each scenario's planned days
node packages/bench/run.mjs --dialogue      # Tier A + Tier B (drives claude -p; costs usage; model pinned to sonnet)
node packages/bench/run.mjs --only carve    # filter scenarios/dialogues by name
node packages/bench/run.mjs 2>&1 | grep -E "^[AB] "   # just the two summary lines
```

A line before the A line says which set ran (`set instance: 5 scenarios …` or `set suggest: 27 scenarios …`).

Run `pnpm build` first: the harness imports the built `@ds/core` and `@ds/server`.

## Tier A

Each scenario is seeded into a `MemoryStore` and its events are applied through the real core tools (`apply_baseline`, `shift_day`, `carve_out`, `carry_over`, `import_as_baseline`, `plan_schedule`, `add_commitment`, `mark_task`, `move_block`, …) with a fixed clock. There are two sets. The default, `scenarios/*.json`, is the product since baseline-first: a baseline week applied to a real week and adjusted by the instance operations. `--suggest` runs `scenarios/suggest/*.json`, the from-scratch planner scenarios (`plan_schedule`), which the product now uses only to suggest a week when no baseline exists. After every event the state is scored. The availability the scorer reads is the one the product reads: the baseline's usable spans (first slot to last slot of each day, minus its busy slots) once a baseline with a task slot exists, else the settings' windows:

| metric | lower is better | meaning |
|---|---|---|
| churn | 0..1 | still-valid blocks the product owns (planner, baseline, adjusted; not hand-placed) that the event moved, resized, or removed; matched by task and time, so a block re-created where it was under a new id is not churn; an event's `allowedChurnBlocks` are not counted, nor the blocks an instance operation was asked to move (see below); not scored after the user's own `move_block` or `add_block` |
| holes | minutes | free availability on days from now on while some task still had budget, counted only up to what the remaining budgets could fill that day; minutes skipped or missed on a day are not fillable that day; a day whose distinct live tasks (any source) reached `maxTasksPerDay` has no fillable holes: its free time is the user's setting |
| blobs | minutes | one task's longest stretch on one day beyond 2 × its session length (blocks parted only by a commitment of ≤ 30 minutes are one stretch) |
| splinters | count | sittings shorter than min(session, budget left before them) when the day, from now on, had room to make them whole: free time beside them, or a free slot elsewhere on the day long enough for them; blocks parted only by a commitment of 30 minutes or less are one sitting; a sitting that has ended is not re-judged. A remainder (shorter than a session, the last of its budget) is free anywhere except as the first block of a day when another task could have opened the day with a whole sitting, or an earlier planned day in the period still had room for it |
| off_segment | minutes | outside a task's preferred segment while that segment still had room from now on (a morning already past is not room) |
| budget_miss | minutes | unmet budget that had usable free time (free time on a day whose distinct live tasks reached `maxTasksPerDay` is not usable, as for `holes`); plus a daily task's whole budget on a planned day where it got no block, the day was under `maxTasksPerDay`, and the weekly sittings placed there could have held one of its sittings (a day at the task cap is the user's setting and is not scored); minutes skipped or missed on a day are not fillable that day |
| must_do_miss | minutes | after a plan that names tasks (`mustDo`), what each named task ends the event short of min(session, budget left before the event) on the window's first available day; blocks already on that day count, and nothing below a block's worth is expected. A named task that did not land is friction whatever the planner's reason |
| switches | count | adjacent task changes per day beyond distinct tasks − 1 |
| late_start | minutes | from the first available minute after now to the first block; a block in progress at now counts as started |
| consistency | count | for each task with live blocks of any source (the user's own placements are the routine) on at least two days from now on (inside the range), the days whose first block starts at a different time of day than the task's usual first start (the most common; ties to the earliest); a task seen on one day has nothing to compare |

Minutes skipped or missed on a day are not fillable that day for `holes` and `budget_miss` (a missed block means not today, like a skipped one).

`friction` is the weighted sum in `weights.json`. Hard constraints (planner block outside availability or overlapping; a manual or baseline block changed by a plan; after an instance operation, a block it laid or moved outside the usable time, overlapping, or under a commitment, or a manual or done block it changed; any block changed by `import_baseline`; an event over 200 ms; a thrown error) count under `crash`. A pending block the product owns (planner, baseline or adjusted) under a commitment or a recurring occurrence is counted after every event (`under`, in the per-scenario line and the summary): after the user's own events the count is information, because a commitment that lands on a block leaves it there until the next plan or operation and the product never auto-plans; after a planner event it is a hard violation, `block_under_commitment`, on any day of the schedule, because the plan knew about the commitment and left its own block under it; after an instance operation it is a hard violation for the blocks the operation laid or moved.

**Which events are scored on what.** Every event is scored for `churn` except the user's own block edits, `move_block` and `add_block`, where the change is the user's (and a thrown error or a slow call counts under `crash` whatever the event). The day-shape metrics (`holes`, `blobs`, `splinters`, `off_segment`, `budget_miss`, `must_do_miss`, `switches`, `late_start`, `consistency`) and the structural hard checks are computed only after the events that change the plan: `plan`, `replan_until`, `clear_schedule`, and the instance events `apply_baseline`, `shift_day`, `carve_out`, `carry_over`, which change the week the product owns. `consistency` is not scored after `shift_day`, `carve_out` or `carry_over` (controller ruling, 2026-10-09): a block one of them moved starts off its usual hour because the user asked for the move, so it is exempt, as for churn; it is scored after `apply_baseline` and the plan events as before. `import_baseline` changes the template, not the week (the week changes when `apply_baseline` lays it), so it is scored for churn and the hard checks only: it must not touch a block, and scoring the empty week after it would measure the ruling that an import does not apply itself. Churn after an instance operation follows a per-event rule (not `allowedChurnBlocks`, which is a count the scenario grants): the blocks the user asked it to move are not churn and stay in the denominator. For `shift_day` that is the rest of today (today's blocks ending after now); for `carve_out`, the carve's day from its start on (blocks that day ending after the carve starts: the user's own interruption, and what it pushes); for `carry_over`, the carried task's own blocks (its next slot may be extended). Anything else an operation moves, a past block or another day, is churn. The product rule is that the other events (`advance`, `mark_done`, `mark_skipped`, `add_commitment`, `extend_availability`, `set_availability`, `move_block`, `add_block`, `save_baseline`) never auto-plan, so scoring the day after one of them measured that ruling, not the planner's friction: a skipped block at 13:00 left the afternoon empty by design, and that one snapshot (holes 270, late_start 240) used to dominate a scenario whose two plans scored 0 and 4. Each metric is averaged over the events that scored it, and a scenario's `friction` is the weighted sum of those means.

Scenario fields: `now`, optional `range` (scored window; default the week of `now`, starting on `settings.weekStartsOn`, Sunday by default since 2026-10-09; the `suggest/` scenarios pin `weekStartsOn: 1` because they were written around Monday-to-Sunday weeks, so their numbers are unchanged), `settings` (partial), `tasks`, `commitments`, `recurring`, `blocks` (pre-existing; default source `manual`), `baseline`, `events`. `baseline` is `{ slots: [...] }`, written with `store.setBaseline` after the tasks: a slot is `{ day: 0-6, start: "HH:MM", end: "HH:MM" }` with `task` (the task's name, resolved to its id by the same slug rule as blocks) or `taskId` for a task slot, or `kind: "busy"` and a `title` for a busy slot; `days: [1, 2, 3, 4, 5]` in place of `day` lays the same slot on several weekdays. Times are local, `YYYY-MM-DDTHH:MM`. Event types: `plan`, `replan_until`, `add_commitment`, `extend_availability`, `set_availability`, `mark_done`, `mark_skipped`, `move_block`, `add_block`, `save_baseline`, `apply_baseline` (`weekOf`), `import_baseline` (`ics`: an .ics file path relative to the scenario file's directory; `run.mjs` passes the directory), `shift_day`, `carve_out` (`from`, `to`, `title`), `carry_over` (`task`), `clear_schedule`, `advance`. A `plan` or `replan_until` event takes `mustDo` (task names) and may carry `allowedChurnBlocks: N`, the number of still-valid blocks it may move or remove without counting as churn: 1 for the one block that gives way to a must-do sitting (`must-do-full-day`). The allowance is on the event, not the scenario, because churn is scored per event and only the must-do plan has earned it; it is a count, not the planner's own `displaced` list, so the planner cannot declare churn away.

### Scenarios

One line each: the setup, then what a tired person opening the app would want to see.

Instance scenarios (`scenarios/`, the default set). All but the import share one baseline: seven daily tasks of an hour each, weekdays 09:00-18:00 with a busy Lunch 12:00-13:00 and 16:00-17:00 left blank (Leetcode, Writing, Reading, Building, Design, Journal, Review in priority order; `shift-day` has no blank hour, Review at 16:00-17:00).

- `apply-week` — Monday 08:00, the baseline applied to this week. The week is the baseline, slot for slot: 35 blocks and five Lunches, nothing moved, nothing under a commitment, the blank hour left blank (churn 0, holes 0, `under` 0).
- `shift-day` — the week applied; at 10:40 a call lands on 11:00-12:00 (over Reading) and the user says "I'm starting now". Writing 10:40-11:00, then Reading, Building, Design and Journal in order from 13:00, each an hour; Review, the lowest priority, no longer fits before 17:00 and is dropped; Leetcode, over unmarked, is missed. The five moved blocks start off their usual hour, which is what the user asked for: `consistency` is not scored after the shift.
- `carve-out` — the week applied; at 13:30 "busy 14:00-15:00" (Dentist). Design and Journal move down an hour in order, the blank hour absorbs the push, Review stays at 17:00; nothing before 14:00 moves (churn 0).
- `carry-over` — the week applied; Leetcode marked done at 10:05, Writing's 10:00-11:00 ended unmarked; at 11:15 "I didn't finish Writing". Writing's hour lands whole in today's blank 16:00-17:00; nothing else moves.
- `import-as-baseline` — Monday 5 Oct 06:00, no tasks; `routine.ics` (the week of 28 Sep: five titles at the same times Monday to Friday, 07:00-21:00 with 11:00-13:00 and 17:00-19:00 blank) imported as the baseline, then applied to this week. The import yields 25 task slots and 5 new tasks (Morning study, LeetCode grinding, ML grinding, Software — system design & engineering, Working — startup build; 600 min a week each, 120-minute sessions), and the week holds the 25 blocks at the calendar's own times (friction 0).

Suggest scenarios (`scenarios/suggest/`, `--suggest`): the from-scratch planner, which since baseline-first runs only when no baseline exists. Opening the app at 21:00:

- `add-weekend-hours` — a planned Friday, then Saturday and Sunday hours added and the week re-planned. Friday untouched; the weekend in whole sittings. Four daily tasks fill the cap of 4, so each day holds one weekly task beside them (Friday, the first plan's only day, takes all of Behavioral's week).
- `early-commitment` — a 09:00 plan with a standup at 09:30. The first 30 minutes used; the sitting continues after the standup.
- `eight-task-week` — four daily and four weekly tasks, deep style; a dentist appointment, then a Wednesday re-plan after one task is done. Only the dentist's hour moves; Wednesday keeps its shape. The cap of 4 holds the four daily tasks and each day one weekly task, the weekly ones alternating.
- `friday-only-week` — Friday 09:00; a weekly task holds this morning's hour and has 60 left, one hour is free after the standup, and another weekly task wants 120. The free hour goes to the task that can finish, whole: with no other day left, the hour is not lost to the no-top-up rule.
- `hand-arranged-friday` — three hand-placed Friday blocks, a week plan, a call, a re-plan. The hand-placed blocks never move; the rest fills around them: AI-assisted coding and one weekly task beside the three hand-placed ones (the cap of 4 plus the day's weekly place).
- `hand-edit-survives` — a day plan, one block dragged to the afternoon by hand, a late-afternoon call over the evening block, a re-plan at 10:30. The dragged block stays put; the hour it left is refilled whole; only the call's block moves.
- `late-start-evening` — opening the app at 21:15 with 75 minutes of evening left. Something short tonight, and tomorrow planned from its first minute.
- `late-week-two-weekly` — Thursday 09:00, two 300-minute weekly tasks in 120-minute sessions and two daily tasks. The daily tasks still get their hour on Thursday; the weekly sittings take what is left, and Friday does not open with a remainder.
- `late-week-weekly` — Thursday 09:00, one 300-minute weekly task in 120-minute sessions and two daily tasks. Two whole sittings Thursday and the remainder Friday; neither a 300-minute blob nor an unmet week.
- `later-block-under-commitment` — a week plan on Monday, a dentist landing on Thursday over a planner block, then a Wednesday day plan. Thursday's block gone and its hour refilled after the dentist, the rest of Thursday untouched: a plan never leaves its own block under a commitment it knows about, whatever day it is on.
- `morning-overflow` — four morning-preferring tasks wanting six hours of a three-hour morning. The top task gets the morning; the others sit whole in the afternoon, not cut in two around noon.
- `must-do-after-hours` — Monday 22:00; tomorrow is already full with five daily tasks (the cap), and "I must do Writing tomorrow". One whole Writing sitting on Tuesday, exactly one block giving way, the rest of Tuesday as it was.
- `must-do-full-day` — a full Monday, then "I must do Writing today" at 09:00. Writing first; at most one block gives way; nothing else moves. With the cap of 4 the first plan holds the four daily tasks and one weekly task; at 09:00 the 07:00 and 08:00 sittings are missed (not today), and Writing takes 09:00 and finishes at 16:00.
- `must-do-half-sitting` — Friday 13:00 with nothing left this week; Monday (08:30-11:30 and 13:30-14:30) is planned full, with a hand-placed half hour of T5 at 11:00, and "I must do T5 Monday" in 75-minute sessions. A whole 75-minute sitting of T5 on Monday beside the half hour, one block giving way; the hand-placed block untouched. A half hour already there is not the sitting the user asked for.
- `priority-ten` — a full day: one 120-minute block of the top task (its whole day) and seven hours of lesser tasks down to priority 8, then a priority-10 task named must-do. The two bottom hours give way, not the top block: the top task keeps its only sitting.
- `remainder-after-lunch` — a 150-minute daily task every morning and a 210-minute weekly task in 90-minute sittings that end at the lunch gap. The last half hour after lunch on the day of its sitting, or after the next morning's task; never alone at 09:00.
- `routine-week` — the week planned on Monday at 07:00: Leetcode, AI learning, Building and Behavioral prep daily, three weekly tasks in 120- and 60-minute sittings. A tired person wants the same thing at the same hour each day: Leetcode after breakfast, Building after lunch. The four daily tasks fill the cap of 4 and each day holds one weekly task beside them, alternating: Startup learning, System design, Startup learning, Morning learning, System design.
- `saturday-only` — availability on Saturday only, a week plan on Wednesday. Saturday planned; no complaint about the empty weekdays.
- `skip-then-replan` — at 11:00 a block still ahead is skipped and the rest of the day re-planned. The in-progress block stays; the skipped task gets nothing more today (skipped means not today); the freed hour goes to other tasks or stays free without a hole. Unchanged by missed-means-not-today (friction 0).
- `something-came-up` — away all morning, the interview not done; at 13:00 "I didn't finish the interview, I'm free until 16:00", which is `plan_schedule` with `must_do` naming the Machine learning interview (`mustDo` on the re-plan). 13:00-15:00 goes to the interview in whole sittings, starting at 13:00. A bare "free until T" after an unmarked morning leaves that task out by design (missed means not today; friction 8.0, late_start 120 averaged over the two scored plans, 240 on the re-plan: 13:00-17:00 empty); naming the unfinished task is what puts it back.
- `standup-cascade` — the eight-task week planned once on Monday, scored over the whole week. The four daily tasks at the same hour each day and one weekly task beside them, alternating; what the one weekly place a day cannot hold is named in the summary; no slivers.
- `tired-evening` — 21:00 Wednesday with 90 minutes left; two 120-minute daily tasks, a 30-minute one, and a 180/week evening task. Tonight the 30 and one whole evening sitting, no 15-minute slivers; Thursday planned from 09:00 with one Reading sitting, the week's third left to Friday (paced: one a day).
- `two-and-a-half-hours` — a weekly task of 150 minutes in 120-minute sessions and a daily hour. The 120 and its 30-minute remainder as one 150-minute stretch: a tired person would rather finish than come back for half an hour another day.
- `two-commitments-day` — a standup and a team sync every day; three weekly tasks with 90-minute sessions whose budgets do not divide (210, 150, 120). Whole 90-minute sittings around the meetings, the tasks on different days; the remainders at the end of a planned day, never alone first thing on a new day.
- `two-weekly-one-day-left` — Friday with two 300-minute weekly tasks unstarted. Whole sittings, two sessions of each and the last day's third where free time remains, not a five-hour blob of one task.
- `varied-style` — eight short tasks, varied style, a lunch added mid-day. Every task once, in its own slot, lunch kept.
- `weekend-sliver-open` — Friday 09:00; a weekly task holds this morning's hour and has 60 left, one hour is free after the standup, and Saturday has a 30-minute window. The hour whole on Friday and Saturday untouched: a half-hour sliver is not an open day to wait for.

## Tier B

Each `dialogues/*.json` seeds a temporary SQLite database, then sends user turns to the real assistant (the server's Claude Code provider, which spawns `claude -p` with the MCP server). Scoring reads tool-call traces only:

| metric | cap | meaning |
|---|---|---|
| tool_acc | | turns where every `expect` tool was called and no `forbid` tool was |
| unrequested | 0 | mutating calls in turns marked `mutating: false`, plus `plan_schedule`/`clear_schedule` calls that were not expected |
| words_med / words_max | 40 / 60 | words per assistant reply |
| questions_max | 1 | question marks per reply |
| setup_turns | 2 | user turns in the setup dialogue (`"setup": true`) until the first mutating call: the one-line Setup reply asks nothing and changes nothing (a read such as `get_setup_status` is fine), so the first change is the user's first task, turn 2, when the script is followed. Lower (1) is a regression: the Setup reply changed the calendar; higher or `-` means the first task was not added when asked (also counted in `tool_acc`) |
| latency_med_s | 20 | seconds per turn |

Turn fields: `user`, `expect`, `forbid`, `mutating` (false when the user asked a question), `noCalls` (true: any tool call makes the turn wrong), `maxQuestions` (the most question marks the reply may hold). Seed fields: `settings`, `tasks`, `baseline` (as in a scenario), `ics` (file next to the dialogue, imported as a calendar before the first turn, so `import_as_baseline {}` finds it), `plan` (`true` or plan args, to start from a planned day), `blocks` with `startIn` and `durationMinutes` in minutes relative to now (dialogues run on the wall clock) and an optional `source` (`baseline` for a week with the baseline applied). The `MUTATING` set and the turn judge are in `src/dialogueScore.mjs`, unit-tested.

Dialogues: `setup` (empty store: "Let's set up my schedule." gets the Setup line with no mutating call and no question; a task, the hours, "Suggest a schedule." gets the must-do question, "just pick" plans), `import-as-baseline` (`routine.ics` on file: "Use my imported calendar as my baseline." → `import_as_baseline`, "Apply it to next week." → `apply_baseline`), `start-my-day` (baseline applied: "I'm starting now." → `shift_day`), `something-came-up` (baseline applied: "busy for the next hour" → `carve_out`), `didnt-finish` (baseline applied, Leetcode over: → `carry_over`), `baseline-next-week` (`save_baseline`, then `apply_baseline`), and the no-baseline ones: `plan-my-day` (the must-do question, then `plan_schedule`), `adjust-friday` (asks before a multi-block change), `where-is-saturday` (answers, changes nothing), `finished-early` (`mark_task`), `move-one-block` (`move_block`). `routine.ics` is dated 28 Sep - 2 Oct 2026 and the import looks back 60 days from the wall clock, so `import-as-baseline` needs a run before 1 Dec 2026 or a re-dated file.

## Tests

`pnpm --filter @ds/bench test` runs the scorer's unit tests (`test/metrics.test.mjs`, the metric definitions above), the replay's (`test/replay.test.mjs`: the `baseline` seed field, each event type on a tiny store, and the five instance scenarios' expected days), and the Tier B judge's (`test/dialogue.test.mjs`).

The default set is now the five instance scenarios; the twenty-seven from-scratch scenarios moved to `scenarios/suggest/` and run with `--suggest`. The metric definitions are unchanged in meaning, with their scope widened to the product's blocks: churn and `under` count baseline and adjusted blocks as well as planner blocks (hand-placed blocks still never count), the availability is the baseline's once one exists, and the instance events are scored as above.
